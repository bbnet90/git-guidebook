Bölüm 01

Git'e Giriş

Versiyon kontrolü nedir, neden gereklidir ve Git dünyasına ilk adım

1.1 — Versiyon Kontrolü Nedir?

Bir proje üzerinde çalışırken kendinizi şu durumda bulmuş olabilirsiniz: rapor_final.docx, rapor_final_v2.docx, rapor_final_SON.docx, rapor_final_SON_gercekten.docx… Bu kaosa çözüm olarak geliştirilen Versiyon Kontrol Sistemleri (VKS), dosyalarınızdaki her değişikliği tarihçesiyle birlikte kayıt altına alır. İstediğiniz zaman geriye dönebilir, kimin ne değiştirdiğini görebilir, paralel olarak farklı özellikler üzerinde çalışabilirsiniz.

VKS'lerin üç nesli vardır:

Nesil Örnek Sistemler Temel Özellik
Yerel RCS Değişiklikler yalnızca kendi bilgisayarınızda tutulur
Merkezi SVN, CVS Tek bir merkezi sunucu; sunucu çökerse tarihçe gider
Dağıtık Git, Mercurial Her kopya tam bir depodur; ağ bağlantısı gerekmez

Git dağıtık bir sistemdir. Bu, deponun tüm tarihçesinin hem sizin bilgisayarınızda hem de sunucuda eksiksiz bulunduğu anlamına gelir. Sunucu çökse bile hiçbir şey kaybetmezsiniz.

1.2 — Git'in Kısa Tarihi

2005 yılına kadar Linux kernel topluluğu, kodlarını yönetmek için BitKeeper adlı ticari bir araç kullanıyordu. Ancak BitKeeper lisans anlaşmazlıkları nedeniyle ücretsiz kullanımını sonlandırınca, Linux'un yaratıcısı Linus Torvalds kolları sıvadı ve sadece birkaç haftada Git'i yazdı.

Torvalds'ın tasarım hedefleri netti: hız, basit yapı, güçlü dal (branch) desteği, tam dağıtık çalışma ve büyük projeleri (Linux kernel gibi) verimli yönetebilme. Git bu hedeflerin hepsini karşıladı ve zamanla dünyanın en yaygın kullanılan versiyon kontrol sistemine dönüştü. Bugün GitHub, GitLab ve Bitbucket gibi platformlar üzerinden milyonlarca proje Git ile yönetilmektedir.

Not "Git" İngiliz argosunda "aptal, beceriksiz biri" anlamına gelir. Torvalds bu ismi bizzat koydu ve "kendi adını her şeye veren ben; bu sefer kötü bir şeye verdim" diye espri yaptı.

1.3 — Kurulum ve İlk Ayarlar

Git'i kullanmaya başlamadan önce sisteminize kurmanız ve kimliğinizi tanımlamanız gerekir. Aşağıda üç işletim sistemi için kurulum komutları yer almaktadır.

# Linux (Debian / Ubuntu) sudo apt update && sudo apt install git # macOS (Homebrew ile) brew install git # Windows — git-scm.com adresinden yükleyici indirin # veya winget ile: winget install --id Git.Git

Kurulum tamamlandıktan sonra yapmanız gereken ilk şey Git'e kim olduğunuzu söylemektir. Bu bilgiler her commit'e otomatik olarak eklenir.

# Kullanıcı adı ve e-posta ayarı (zorunlu) git config --global user.name "Adınız Soyadınız" git config --global user.email "email@example.com" # Varsayılan metin editörünü ayarlama git config --global core.editor "code --wait" # VS Code git config --global core.editor "nano" # Nano # Tüm ayarları listele ve doğrula git config --list

--global bayrağı bu ayarların sistemdeki tüm projeler için geçerli olduğu anlamına gelir. Ayarlar ~/.gitconfig dosyasında saklanır. Belirli bir proje için farklı bir kimlik kullanmak istiyorsanız, proje klasörü içinde --global yerine --local kullanın.

İpucu Varsayılan dal adını main olarak ayarlamak artık yaygın bir pratik haline geldi. Bunu şimdi yapın: git config --global init.defaultBranch main

1.4 — Git'in Çalışma Mantığı

Git'i anlamanın en kritik adımı şudur: Git, dosyalar arasındaki farkları değil, dosyaların anlık görüntülerini (snapshot) saklar. Her commit, o anki projenizin tam bir fotoğrafıdır.

Git'te her değişiklik üç farklı aşamadan geçer:

┌─────────────────────┐ git add ┌──────────────────────┐ git commit ┌──────────────────┐ │ Working Directory │ ─────────────▶ │ Staging Area │ ────────────────▶ │ Repository │ │ (Çalışma Dizini) │ │ (Sahne / Index) │ │ (.git klasörü) │ │ │ ◀───────────── │ │ │ │ │ Dosyaları düzenle │ git restore │ Commit'e hazır olan │ │ Kalıcı tarihçe │ │ ve kaydet │ │ değişiklikler │ │ saklanır │ └─────────────────────┘ └──────────────────────┘ └──────────────────┘
Alan Nerede? Ne içerir?
Working Directory Proje klasörünüz Üzerinde çalıştığınız dosyalar — kaydedilmiş ya da değil
Staging Area .git/index Bir sonraki commit'e dahil edilecek değişiklikler
Repository .git/ klasörü Tüm commit geçmişi ve meta veri

Staging Area neden var? Çünkü bazen bir oturumda birden fazla şeyi değiştirirsiniz ama hepsini tek bir commit'e koymak istemezsiniz. Staging Area size seçicilik hakkı tanır: "Bu değişikliği şimdi commit'le, şunu henüz değil."

Dikkat .git/ klasörünü asla elle silmeyin veya düzenlemeyin. Bu klasör projenizin tüm tarihçesini içerir. Silerseniz her şeyi kaybedersiniz.

1.5 — Özet

Konu Önemli Nokta
Versiyon Kontrolü Değişiklikleri zaman damgasıyla saklar; geri dönmeyi mümkün kılar
Git'in Yapısı Dağıtık: her kopya tam bir depodur, sunucuya bağımlı değilsiniz
İlk Kurulum git config --global user.name ve user.email şart
Üç Alan Working Directory → Staging Area → Repository akışını ezberleyin
Snapshot Modeli Git fark değil, anlık görüntü saklar — bu çok önemli bir ayrım

Bölüm 02

Temel Komutlar

Günlük Git kullanımının bel kemiği — init, add, commit, log ve daha fazlası

2.1 — Depo Başlatma: git init

Her şey bir git init komutuyla başlar. Bu komut, bulunduğunuz klasörü bir Git deposuna dönüştürür ve içinde .git/ adlı gizli bir klasör oluşturur. Tüm versiyon tarihçesi bu klasörde saklanır.

# Mevcut klasörü depoya dönüştür git init # Yeni klasör oluştur ve içini depoya dönüştür git init proje-adi # İnit sonrası .git klasörünün varlığını doğrula ls -la # .git görünmeliydi

.git/ klasörünün içinde ne var? Kısaca: her şey. Commit nesneleri, dal referansları, konfigürasyon dosyası, hook'lar… Bu klasörü silmek deponuzu sıradan bir klasöre dönüştürür ve tüm tarihçeyi yok eder.

Not Zaten var olan bir klasörü git init ile başlatmak güvenlidir — mevcut dosyalarınıza dokunmaz, sadece .git/ ekler.

2.2 — Durumu Kontrol Etme: git status

Git kullanırken en sık çalıştıracağınız komuttur. Hangi dosyaların değiştiğini, hangilerinin sahnelendiğini (staged), hangilerinin Git tarafından hiç takip edilmediğini gösterir.

git status # Daha kısa çıktı için git status -s

git status çıktısında karşılaşacağınız durumlar:

Durum Anlamı
Untracked files Git'in hiç haberi olmayan yeni dosyalar
Changes not staged Takip edilen ama henüz sahnelenmeyen değişiklikler
Changes to be committed Sahnelenmiş, bir sonraki commit'e girecek değişiklikler
nothing to commit Her şey temiz, kaydedilecek değişiklik yok

2.3 — Değişiklikleri Sahnelemek: git add

Working Directory'deki değişikliklerinizi Staging Area'ya (sahne) taşır. Commit'e neyin gireceğine siz karar verirsiniz — bu seçicilik güçtür.

# Tek bir dosyayı sahneye al git add index.html # Belirli bir klasörü sahneye al git add src/ # Tüm değişiklikleri sahneye al git add . # Hangi parçaların sahneleneceğini tek tek seç (interaktif) git add -p

git add -p (patch) komutu özellikle güçlüdür: aynı dosyadaki farklı değişiklikleri ayrı ayrı incelemenizi ve hangilerini sahneleyeceğinizi seçmenizi sağlar. Büyük değişiklik setlerini küçük, anlamlı commit'lere bölmek istediğinizde vazgeçilmezdir.

İpucu git add . ile tüm değişiklikleri sahnelemeden önce git status ile ne eklediğinizi kontrol edin. İstemeden büyük binary dosyalar veya hassas bilgiler sahneliyebilirsiniz.

2.4 — Değişiklikleri Kaydetmek: git commit

Commit, Staging Area'daki değişikliklerin depoya kalıcı olarak kaydedilmesidir. Her commit'in benzersiz bir SHA-1 hash'i vardır (örn: a3f9c2d) ve bu hash değişmez — Git'in güvenilirliğinin temeli budur.

# Mesajla commit git commit -m "feat: kullanıcı giriş formu eklendi" # Editörde uzun mesaj yaz git commit # Takip edilen dosyaları sahneleyip commit et (git add + commit) git commit -am "fix: hata mesajı düzeltildi" # Son commit mesajını veya içeriğini değiştir git commit --amend

İyi bir commit mesajı nasıl yazılır? Dünyada yaygınlaşan Conventional Commits standardı şu formatı önerir:

# Format: <tip>: <kısa açıklama> feat: yeni özellik eklendi fix: hata düzeltildi docs: dokümantasyon güncellendi style: kod biçimlendirmesi (mantık değişikliği yok) refactor: kod yeniden yapılandırıldı test: test eklendi veya düzenlendi chore: yapılandırma, bağımlılık güncellemesi

Atomic commit prensibi: Her commit tek bir iş yapmalıdır. "Birkaç şeyi düzelttim" diye yazılan commit'ler ileride tarihçeyi anlamayı zorlaştırır. "Hata düzelt, yeni özellik ekle, CSS güncelle" üç farklı commit olmalıdır.

Dikkat git commit --amend son commit'i değiştirir. Bu commit zaten uzak sunucuya push edilmişse asla amend etmeyin — ekip arkadaşlarınızın tarihçesi bozulur.

2.5 — Geçmişi Görüntülemek: git log

Deponun commit tarihçesini görüntüler. Varsayılan çıktı oldukça ayrıntılıdır; bayraklar ile istediğiniz formata getirebilirsiniz.

# Standart log git log # Her commit tek satırda git log --oneline # Dal yapısını grafiksel göster git log --oneline --graph --all # Belirli bir yazarın commit'leri git log --author="Enes" # Son 5 commit git log -5 # Belirli tarihten sonraki commit'ler git log --since="2024-01-01" # Belirli bir commit'in detaylarını gör git show a3f9c2d

Çok kullandığınız log formatını alias olarak kaydedebilirsiniz:

git config --global alias.lg "log --oneline --graph --all --decorate" # Artık sadece: git lg

2.6 — Değişiklikleri Karşılaştırmak: git diff

Dosyalar arasındaki farkları satır satır gösterir. Neyi commit etmek üzere olduğunuzu anlamak için son derece kullanışlıdır.

# Working directory ile staging arasındaki fark git diff # Staged (sahnelenen) değişiklikler ile son commit arasındaki fark git diff --staged # İki commit arasındaki fark git diff abc123 def456 # İki dal arasındaki fark git diff main feature/login
Not git diff çıktısında + ile başlayan satırlar eklenenler, - ile başlayanlar silinenleri gösterir. Kırmızı = silinen, yeşil = eklenen (terminal renkleri aktifse).

2.7 — Dosya İşlemleri

Dosyaları silmek, taşımak veya değişiklikleri geri almak için Git'in kendi komutlarını kullanmak önemlidir — böylece Git bu değişiklikleri otomatik olarak takip eder.

# Dosyayı hem diskten hem de Git'ten sil git rm gereksiz-dosya.txt # Dosyayı Git'ten kaldır ama diskte bırak (.gitignore için ideal) git rm --cached hassas-bilgi.env # Dosyayı yeniden adlandır veya taşı git mv eski-ad.txt yeni-ad.txt # Çalışma dizinindeki değişikliği geri al (staged değilse) git restore degistigim-dosya.txt # Sahnelemeyi geri al (commit etme ama unstage yap) git restore --staged yanlis-sahnelenen.txt # Takip edilmeyen dosyaları temizle (dikkatli kullan!) git clean -fd
Dikkat git restore ve git clean ile yapılan değişiklikler geri alınamaz. Emin olmadan çalıştırmayın. git clean -n ile önce neyin silineceğini önizleyin.

2.8 — Özet ve Hızlı Başvuru

Bu bölümün tüm komutları tek tabloda:

Komut Ne yapar?

git statusDeğişikliklerin durumunu gösterir
git add .Tüm değişiklikleri sahneye alır
git add -pDeğişiklikleri parça parça sahneye alır
git commit -mSahnelenen değişiklikleri kaydeder
git commit --amendSon commit'i düzenler (push edilmemişse)

Bölüm 03

Uzak Depolar

GitHub ve benzeri platformlarla çalışmak — clone, push, pull, fetch ve SSH

3.1 — Remote Nedir?

Şimdiye kadar yaptığımız her şey yalnızca kendi bilgisayarımızda kaldı. Gerçek dünyada kodunuzu başkalarıyla paylaşmanız, yedeklemeniz ya da bir sunucudan erişmeniz gerekir. Bunun için uzak depo (remote) kavramı devreye girer.

Remote, deponuzun internet üzerindeki bir kopyasıdır. GitHub, GitLab, Bitbucket gibi platformlar bu kopyayı barındırır. Yerel deponuz ile uzak depo birbirinden bağımsızdır; siz istediğinizde senkronize edersiniz.

# Mevcut remote bağlantılarını listele git remote -v # Yeni bir remote ekle git remote add origin https://github.com/kullanici/repo.git # Remote'u yeniden adlandır git remote rename origin yeni-isim # Remote'u kaldır git remote remove origin

Origin neden "origin" denir? Bu bir kural değil, gelenektir. git clone ile bir depoyu kopyaladığınızda Git, uzak depoyu otomatik olarak origin olarak adlandırır. Başka bir isim de verebilirsiniz ama origin o kadar yaygınlaşmıştır ki ekipler bunu standart kabul eder.

3.2 — HTTPS ve SSH: Bağlantı Yöntemleri

Uzak depoya bağlanmanın iki yolu vardır. Her commit push ettiğinizde hangisini kullandığınız fark yaratır.

Yöntem URL Formatı Kimlik Doğrulama Öneri
HTTPS https://github.com/kullanici/repo.git Kullanıcı adı + token her seferinde Hızlı başlangıç için
SSH git@github.com:kullanici/repo.git Bir kez anahtar kurulumu, sonra otomatik Günlük kullanım için

SSH anahtarı kurmak için:

# 1. Yeni bir SSH anahtar çifti oluştur ssh-keygen -t ed25519 -C "email@example.com" # 2. SSH agent'ı başlat ve anahtarı ekle eval "$(ssh-agent -s)" ssh-add ~/.ssh/id_ed25519 # 3. Açık anahtarı kopyala (GitHub'a eklenecek) cat ~/.ssh/id_ed25519.pub # 4. Bağlantıyı test et ssh -T git@github.com

Adım 3'teki çıktıyı kopyalayın, GitHub'da Settings → SSH and GPG Keys → New SSH Key yolunu izleyerek yapıştırın. Artık her push/pull'da şifre girmenize gerek kalmaz.

İpucu Mevcut bir HTTPS remote'u SSH'a çevirmek isterseniz: git remote set-url origin git@github.com:kullanici/repo.git

3.3 — Depoyu Kopyalamak: git clone

Uzak bir deponun tüm tarihçesiyle birlikte yerel kopyasını oluşturur. Klonlama sonrasında Git otomatik olarak uzak depoyu origin adıyla ekler ve varsayılan dalı takip etmeye başlar.

# HTTPS ile klonla git clone https://github.com/kullanici/repo.git # SSH ile klonla git clone git@github.com:kullanici/repo.git # Farklı bir klasör adıyla klonla git clone git@github.com:kullanici/repo.git benim-proje # Sadece son commit'i indir (büyük repolarda hız için) git clone --depth 1 https://github.com/kullanici/repo.git # Belirli bir dal ile klonla git clone --branch develop https://github.com/kullanici/repo.git

Klonlama sonrasında oluşan yapı:

repo/ ├── .git/ # Tüm tarihçe burada ├── .git/config # origin remote'u burada tanımlı └── ...proje dosyaları...

3.4 — git fetch ve git pull Farkı

Bu iki komut sık karıştırılır. Aralarındaki fark kritiktir:

Komut Ne yapar? Çalışma dizinine dokunur mu?
git fetch Uzaktaki değişiklikleri indirir, uygulama yapmaz Hayır — güvenli
git pull fetch + merge işlemini tek adımda yapar Evet — dosyalarınız değişir
# Uzaktaki değişiklikleri indir, birleştirme (merge) yapma git fetch origin # Neyin geldiğini gör, sonra karar ver git log HEAD..origin/main --oneline # Şimdi birleştir git merge origin/main # Ya da fetch + merge yerine doğrudan pull git pull origin main # Merge yerine rebase ile pull (daha temiz tarihçe) git pull --rebase origin main
İpucu Takım ortamında çalışırken git pull yerine önce git fetch yapıp neyin geldiğini görmek, sonra merge ya da rebase kararı vermek daha güvenli bir alışkanlıktır.

3.5 — Değişiklikleri Göndermek: git push

Yerel commit'lerinizi uzak depoya gönderir. Push etmek için uzak depoda push ettiğinizden daha yeni commit'ler olmamalıdır; varsa önce pull yapmanız gerekir.

# İlk push — upstream bağlantısını kur git push -u origin main # Sonraki push'lar — upstream kurulduktan sonra kısa yol git push # Belirli dal push git push origin feature/login # Tüm etiketleri gönder git push --tags # Uzak daldaki commit'lerin üzerine yaz (tehlikeli!) git push --force-with-lease origin main
Dikkat — Force Push --force yerine daima --force-with-lease kullanın. --force uzak daldaki her şeyin üzerine körce yazar; --force-with-lease ise uzakta sizin bilmediğiniz commit'ler varsa reddeder ve veri kaybını önler.

3.6 — Fork ve Pull Request Kültürü

Açık kaynak projelere ya da başkasının deposuna katkıda bulunmak istediğinizde doğrudan push edemezsiniz. Bunun için fork iş akışı kullanılır.

# Fork iş akışı # 1. GitHub'da projeyi fork'la (web üzerinde) # 2. Fork'unuzu klonla git clone git@github.com:SENİN_KULLANICI/repo.git # 3. Orijinal repoyu upstream olarak ekle git remote add upstream git@github.com:ORIJINAL/repo.git # 4. Upstream'den güncellemeleri al git fetch upstream git merge upstream/main # 5. Özellik dalında çalış, push et git push origin feature/benim-katkim # 6. GitHub'da Pull Request aç (web üzerinde)

Pull Request (PR) ya da GitLab'da Merge Request (MR), yaptığınız değişikliklerin ana depoya alınmasını talep ettiğiniz bir süreçtir. Ekip arkadaşlarınız kodunuzu inceler (code review), geri bildirim verir ve onaylandıktan sonra merge edilir.

3.7 — Özet ve Hızlı Başvuru

Komut Ne yapar?
git remote -vBağlı uzak depoları listeler
git remote addYeni uzak depo bağlantısı ekler
git clone <url>Uzak depoyu yerel kopyalar
git fetch originUzaktaki değişiklikleri indirir, uygulamaz
git pull origin mainİndirir + mevcut dala birleştirir
git pull --rebaseİndirir + rebase ile uygular (temiz tarihçe)
git push -u origin mainİlk push + upstream bağlantısı kurar
git push --force-with-leaseGüvenli zorla gönderme

Bölüm 04

Dallar ve Birleştirme

Paralel geliştirmenin temeli — branch, merge ve çatışma çözümü

4.1 — Dal (Branch) Mantığı

Bir dal, aslında bir commit'e işaret eden hafif bir pointer'dan başka bir şey değildir. Dosya kopyalanmaz, klasör oluşmaz — sadece 40 karakterlik bir SHA-1 hash'ine işaret eden küçük bir referans yaratılır. Bu yüzden Git'te dal oluşturmak neredeyse anlık ve bedavadır.

main │ A ─── B ─── C ─── D │ │ │ └── E ─── F │ feature/login └──┘

HEAD özel bir pointer'dır — şu anda hangi dalda, hangi commit'te olduğunuzu gösterir. Normalde HEAD bir dalı işaret eder (örn: main), o dal da bir commit'i işaret eder.

Bazen HEAD doğrudan bir commit'i işaret eder, herhangi bir dala bağlı değildir. Buna detached HEAD denir. Genelde eski bir commit'i incelemek için git checkout <hash> yaptığınızda oluşur. Bu durumda yaptığınız yeni commit'ler hiçbir dala ait olmaz — dikkatli olun.

Dikkat — Detached HEAD Detached HEAD durumundayken commit yaparsanız ve başka bir dala geçerseniz, o commit'ler kaybolabilir (reflog ile kurtarılabilir ama riskli). Çalışmaya devam edecekseniz önce git switch -c yeni-dal ile bir dal oluşturun.

4.2 — Dal İşlemleri

Modern Git'te dal işlemleri için git switch ve git checkout birlikte kullanılabilir; switch daha yeni ve daha az kafa karıştırıcıdır çünkü sadece dal işlemlerine odaklanır.

# Yeni dal oluştur (geçmeden) git branch feature/login # Var olan dala geç git switch feature/login # eski yöntem: git checkout feature/login # Dal oluştur VE hemen geç (en çok kullanılan) git switch -c feature/login # eski yöntem: git checkout -b feature/login # Tüm yerel dalları listele git branch # Uzak dalları da göster git branch -a # Detaylı bilgiyle listele (son commit, takip durumu) git branch -vv # Dalı sil (güvenli — merge edilmemişse hata verir) git branch -d feature/login # Dalı zorla sil (merge edilmemiş olsa bile) git branch -D feature/login # Dalı yeniden adlandır git branch -m eski-isim yeni-isim
İpucu Dal isimlendirmede yaygın kural: feature/özellik-adı, fix/hata-adı, hotfix/acil-düzeltme. Bu, hangi dalın ne amaçla açıldığını herkes için netleştirir.

4.3 — Birleştirme: git merge

Merge, bir dalın değişikliklerini başka bir dala entegre eder. İki farklı senaryo vardır ve sonuçları çok farklıdır.

Senaryo Ne olur?
Fast-forward merge Ana dal hiç ilerlememişse, pointer sadece ileri kaydırılır. Yeni merge commit oluşmaz.
3-way merge Her iki dal da ayrı commit'ler almışsa, Git ortak ataya bakarak bir merge commit oluşturur.
# main dalına geç, sonra feature dalını içine al git switch main git merge feature/login # Fast-forward mümkün olsa bile merge commit oluştur git merge --no-ff feature/login # Tüm dalın commit'lerini TEK bir commit'e sıkıştırarak birleştir git merge --squash feature/login git commit -m "feat: giriş sistemi eklendi"

--no-ff tercih eden ekipler çoğunlukla şunu ister: her özelliğin ayrı bir dal olarak tarihçede görünmesi, hatta fast-forward mümkün olsa bile. Bu, "bu commit'ler bir özellik dalıydı" bilgisini korur.

--squash ise özellikle çok sayıda küçük "wip", "typo fix" commit'i içeren dalları ana dala tek, temiz bir commit olarak eklemek istediğinizde kullanışlıdır.

4.4 — Çatışma Çözümü (Conflict Resolution)

İki dal aynı dosyanın aynı satırını farklı şekillerde değiştirmişse, Git hangisinin doğru olduğuna karar veremez ve size bırakır. Buna merge conflict denir.

Git, çatışan dosyanın içine özel işaretler ekler:

<<<<<<< HEAD const apiUrl = "https://api.example.com/v1"; ======= const apiUrl = "https://api.example.com/v2"; >>>>>>> feature/api-update

<<<<<<< HEAD ile ======= arası sizin dalınızdaki (şu an bulunduğunuz dal) versiyon; ======= ile >>>>>>> arası birleştirmeye çalıştığınız dalın versiyonudur.

Çözüm adımları:

# 1. Çatışan dosyaları bul git status # 2. Dosyayı editörde aç, işaretleri kaldır, # doğru içeriğe manuel olarak karar ver # 3. Çözülen dosyayı sahnele git add dosya-adi.js # 4. Tüm çatışmalar çözüldükten sonra commit et git commit # Vazgeçmek isterseniz merge'i tamamen iptal edin git merge --abort

VS Code, IntelliJ gibi modern editörler çatışmaları görsel olarak gösterir ve "Accept Current", "Accept Incoming", "Accept Both" gibi tek tıkla çözüm butonları sunar. Büyük çatışmalarda git mergetool komutu ile harici bir birleştirme aracı da açabilirsiniz.

Not Çatışmadan korkmayın — bu Git'in kötü çalıştığı anlamına gelmez, tam tersine güvenlik önlemidir. Git, sizin onayınız olmadan hiçbir kod satırını sessizce üzerine yazmaz.

4.5 — Özet ve Hızlı Başvuru

Komut Ne yapar?

git switch -c adYeni dal oluşturur ve geçer
git branch -d adDalı güvenli şekilde siler
git merge dal-adıBelirtilen dalı mevcut dala birleştirir
git merge --no-ffHer zaman merge commit oluşturur
git merge --squashDalı tek commit olarak sıkıştırır
git merge --abortÇatışmalı merge'i iptal eder

Bölüm 05

İleri Git Teknikleri

Tarihi yeniden yazan araçlar — rebase, stash, cherry-pick, reset, reflog

5.1 — Geçmişi Yeniden Düzenlemek: git rebase

Rebase, bir dalın commit'lerini alıp başka bir noktanın üzerine yeniden uygular. Sonuç olarak tarihçe doğrusal görünür — sanki dal hiç ayrılmamış gibi. Merge ise iki dalın birleştiğini gösteren bir merge commit bırakır.

# Merge sonrası tarihçe (dallanma görünür) A ─── B ─── C ─── M ← M bir merge commit ╲ ╱ D ─── E # Rebase sonrası tarihçe (doğrusal, temiz) A ─── B ─── C ─── D' ─── E' ← D ve E yeniden yazıldı
# feature dalındayken main'i baz al git switch feature/login git rebase main # Rebase sırasında çatışma çıkarsa # çatışmayı çöz, sonra: git add . git rebase --continue # Rebase'i tamamen iptal et git rebase --abort

Interactive Rebase en güçlü Git araçlarından biridir. Son N commit'i tekrar açar ve her birini düzenlemenize, birleştirmenize ya da silmenize izin verir.

# Son 4 commit'i interaktif düzenle git rebase -i HEAD~4

Açılan editörde her commit için kullanabileceğiniz komutlar:

Komut Ne yapar?
pickCommit'i olduğu gibi bırak
rewordCommit mesajını değiştir
editCommit içeriğini değiştir
squashBir önceki commit ile birleştir, mesajları birleştir
fixupBir önceki commit ile birleştir, bu commit'in mesajını at
dropBu commit'i tarihçeden tamamen sil
Altın Kural Rebase, commit'leri yeniden yazar. Push edilmiş ve başkaları tarafından kullanılan commit'leri asla rebase etmeyin — ekip arkadaşlarınızın tarihçesi bozulur ve ciddi sorunlara yol açar. Rebase yalnızca henüz push etmediğiniz yerel commit'ler için güvenlidir.

5.2 — Değişiklikleri Geçici Saklamak: git stash

Bir özellik üzerinde çalışırken beklenmedik bir hata bildirimi geldi ve başka bir dala geçmeniz gerekiyor — ama yarım kalan işinizi commit etmek istemiyorsunuz. git stash tam bu an içindir: değişikliklerinizi geçici olarak bir kenara kaldırır, çalışma dizinini temizler.

# Tüm değişiklikleri sakla git stash # Açıklama ekleyerek sakla (önerilir) git stash push -m "login formunu yarıda bıraktım" # Takip edilmeyen (untracked) dosyaları da sakla git stash push -u # Saklananları listele git stash list # Belirli bir stash'ın içeriğini göster git stash show -p stash@{0} # Son stash'ı geri getir ve listeden kaldır git stash pop # Geri getir ama listede bırak git stash apply stash@{1} # Belirli stash'ı sil git stash drop stash@{0} # Tüm stash'ları temizle git stash clear
İpucu git stash pop yerine git stash apply kullanmak daha güvenlidir — değişiklikler geri gelirken çatışma çıkması halinde stash listede kalmaya devam eder ve kaybetmezsiniz.

5.3 — Seçici Commit Taşıma: git cherry-pick

Başka bir dalda bulunan belirli bir commit'i — ve yalnızca onu — mevcut dalınıza uygulamak istiyorsunuz. Tüm dalı merge etmek istemiyorsunuz. İşte cherry-pick tam bunu yapar.

# Tek commit'i taşı git cherry-pick a3f9c2d # Birden fazla commit git cherry-pick a3f9c2d b7e1f3a # Commit aralığı (a dahil değil, b dahil) git cherry-pick a3f9c2d..b7e1f3a # Commit et ama sahnelenmiş bırak (commit etme) git cherry-pick -n a3f9c2d # Çatışma çıkarsa, çöz ve devam et git cherry-pick --continue # İptal et git cherry-pick --abort

Ne zaman kullanılır? Örneğin: develop dalında keşfettiğiniz kritik bir güvenlik düzeltmesini main dalına da uygulamanız gerekiyor ama develop'taki diğer yarım kalan özellikler henüz hazır değil. Sadece o commit'i cherry-pick edersiniz.

5.4 — Geri Alma: git reset ve git revert

Bir hatayı geri almak için iki farklı araç vardır. Hangisini seçeceğiniz o commit'in push edilip edilmediğine bağlıdır.

Araç Ne yapar? Tarihçeyi değiştirir mi? Ne zaman kullan?
git reset HEAD'i geri taşır Evet Henüz push edilmemiş commit'ler
git revert Geri alma commit'i oluşturur Hayır (ekler) Push edilmiş, paylaşılan commit'ler
# ── git reset ────────────────────────────── # Son commit'i geri al, dosyalar staged kalır git reset --soft HEAD~1 # Son commit'i geri al, dosyalar unstaged olur (varsayılan) git reset --mixed HEAD~1 # Son commit'i geri al VE dosya değişikliklerini de sil git reset --hard HEAD~1 # Belirli bir commit'e geri dön git reset --hard a3f9c2d # ── git revert ───────────────────────────── # Belirli commit'i geri alan yeni bir commit oluştur git revert a3f9c2d # Birden fazla commit'i revert et git revert HEAD~3..HEAD # Commit etmeden sahneye al (birden fazla revert'i tek commit'e topla) git revert -n a3f9c2d
Dikkat — git reset --hard --hard ile yapılan reset, working directory'deki kaydedilmemiş değişiklikleri geri dönüşsüz siler. Commit edilmemiş çalışmanızı kaybedersiniz. Her zaman önce git status ile durumu kontrol edin.

5.5 — Kurtarma Ağı: git reflog

Git'in en güçlü güvenlik özelliklerinden biri — çoğu kullanıcının farkında olmadığı reflog. Git, HEAD'in her hareket ettiği anı kaydeder: her commit, her checkout, her merge, her rebase… Hepsini 90 gün boyunca saklar.

git reset --hard ile commit'lerinizi "sildiyseniz" ya da yanlış bir rebase yaptıysanız, reflog sayesinde geri dönebilirsiniz.

# Tüm HEAD hareketlerini gör git reflog # Örnek çıktı: # a3f9c2d HEAD@{0}: reset: moving to HEAD~1 # b7e1f3a HEAD@{1}: commit: feat: login eklendi ← kayıp commit! # c2d4a1b HEAD@{2}: commit: fix: hata düzeltildi # Kayıp commit'e geri dön git reset --hard HEAD@{1} # Ya da o commit'ten yeni bir dal başlat git switch -c kurtarilan-dal HEAD@{1}
İpucu Git'te bir şeyi "gerçekten" silmek düşündüğünüzden çok daha zordur. Commit ettiyseniz, reflog sizi kurtarır. Paniklemeden önce her zaman git reflog çalıştırın.

5.6 — Hatayı Bulmak: git bisect

"Dün çalışıyordu, bugün çalışmıyor" — hangi commit hatayı üretti? Yüzlerce commit arasında manuel arama yapmak yerine git bisect, ikili arama (binary search) algoritması ile hatayı üreten commit'i logaritmik sürede bulur.

# Bisect başlat git bisect start # Şu anki commit bozuk git bisect bad # Bildiğiniz çalışan commit'i işaretle git bisect good v1.2.0 # Git sizi ortadaki commit'e götürür # Test edin, sonucu bildirin: git bisect good # bu commit çalışıyor git bisect bad # bu commit bozuk # Git sonunda hatayı üreten commit'i gösterir # Bitirince orijinal dala dön git bisect reset

100 commit arasında aramayı düşünün: manuel 100 test yerine bisect sadece 7 adımda bulur (log₂100 ≈ 7). Bir test script'i varsa süreci tamamen otomatize de edebilirsiniz: git bisect run ./test.sh

git stash push -mDeğişiklikleri isimli olarak sakla

Bölüm 06

Profesyonel İş Akışları

Ekip ortamında Git — Git Flow, hooks, submodules, etiketleme ve güvenlik

6.1 — Dal Stratejileri

Tek kişilik projede her şeyi main'e commit etmek işe yarayabilir. Ama bir ekipte onlarca geliştirici aynı kod tabanında çalışırken, kimin ne zaman nereye push ettiğini yönetmek bir strateji gerektirir. Yaygın üç yaklaşım şunlardır:

Strateji Dallar En iyi olduğu yer
Git Flow main, develop, feature/*, release/*, hotfix/* Planlı sürüm döngüsü olan ürünler
GitHub Flow main + kısa ömürlü feature dalları Sürekli dağıtım (CI/CD) yapan ekipler
Trunk-based Tek main dalı, çok kısa ömürlü dallar Küçük, hızlı hareket eden ekipler

Git Flow nasıl çalışır:

# main → her zaman production-ready, etiketli sürümler # develop → bir sonraki sürüm için entegrasyon dalı # feature → her özellik kendi dalında gelişir # release → sürüm öncesi son düzeltmeler # hotfix → canlıdaki acil düzeltmeler # Yeni özellik başlat git switch -c feature/odeme-sistemi develop # Özellik bitti, develop'a merge et git switch develop git merge --no-ff feature/odeme-sistemi git branch -d feature/odeme-sistemi # Sürüm dalı aç git switch -c release/1.2.0 develop # Sürümü main ve develop'a merge et git switch main git merge --no-ff release/1.2.0 git tag -a v1.2.0 -m "Sürüm 1.2.0"
İpucu Hangi stratejiyi seçeceğiniz takımın büyüklüğüne, dağıtım sıklığına ve ürünün olgunluk seviyesine bağlıdır. Çoğu modern ekip GitHub Flow'u tercih eder — basit ve CI/CD ile mükemmel uyum sağlar.

6.2 — Sürüm Etiketleme: git tag

Tag'ler belirli commit'lere kalıcı isimler verir. Genellikle yazılım sürümlerini işaretlemek için kullanılır. İki türü vardır:

Tür Nedir? Ne zaman kullan?
Lightweight tag Sadece bir commit hash işaretçisi Kişisel, geçici işaretler
Annotated tag Mesaj, tarih, imzalayan bilgisi içerir Resmi sürümler — bu tercih edilmeli
# Annotated tag oluştur (önerilir) git tag -a v1.0.0 -m "İlk kararlı sürüm" # Lightweight tag git tag v1.0.0-beta # Geçmişteki bir commit'i etiketle git tag -a v0.9.0 a3f9c2d -m "Beta sürümü" # Tüm tag'leri listele git tag # Pattern ile filtrele git tag -l "v1.*" # Tag'i uzak depoya gönder (push tag'leri otomatik göndermez!) git push origin v1.0.0 # Tüm tag'leri push et git push origin --tags # Tag sil (yerel) git tag -d v1.0.0-beta # Tag sil (uzak) git push origin --delete v1.0.0-beta

Sürüm numaralandırmasında evrensel standart Semantic Versioning'dir: MAJOR.MINOR.PATCH — örneğin v2.1.4. MAJOR kırıcı değişiklik, MINOR yeni özellik, PATCH hata düzeltmesi anlamına gelir.

6.3 — Otomasyonlar: Git Hooks

Git hooks, belirli Git olaylarından önce veya sonra otomatik çalışan script'lerdir. .git/hooks/ klasöründe saklanır. Kod kalitesini zorlamak, test çalıştırmak, commit mesajı formatını kontrol etmek için idealdir.

Hook Ne zaman çalışır? Tipik kullanım
pre-commit git commit çalışmadan önce Lint, format, birim testleri
commit-msg Commit mesajı yazıldıktan sonra Conventional Commits formatını zorla
pre-push git push çalışmadan önce Entegrasyon testleri, build kontrolü
post-commit Commit tamamlandıktan sonra Bildirim gönderme, log tutma
post-merge Merge tamamlandıktan sonra Bağımlılıkları güncelle (npm install)

Örnek bir pre-commit hook:

#!/bin/sh # .git/hooks/pre-commit — çalıştırılabilir olmalı (chmod +x) # ESLint ile kod kalitesini kontrol et npx eslint src/ # ESLint hata verdiyse commit'i engelle if [ $? -ne 0 ]; then echo "Lint hataları var. Commit iptal edildi." exit 1 fi

6.4 — Bağımlı Depolar: git submodule

Projeniz başka bir Git deposunu içinde barındırması gerektiğinde (paylaşılan bir kütüphane, tema, ya da ortak araçlar gibi) submodule kullanılır. Ana deponuz, submodule'ün hangi commit'te olduğunu takip eder — dosya içeriğini değil.

# Submodule ekle git submodule add https://github.com/ornek/kutüphane.git lib/kutuphane # Submodule içeren bir repoyu klonla git clone --recurse-submodules https://github.com/ornek/repo.git # Klonladıktan sonra submodule'leri başlat git submodule update --init --recursive # Tüm submodule'leri güncelle git submodule update --remote # Submodule durumunu gör git submodule status
Dikkat — Submodule Tuzakları Submodule'ler karmaşık olabilir: klonlarken --recurse-submodules unutulursa klasörler boş gelir; güncelleme yapıldığında ana repoda commit atmayı unutmak yaygın bir hatadır. Alternatif olarak git subtree daha basit ama daha az esnek bir seçenektir.

6.5 — Görmezden Gelmek: .gitignore

Her projede Git'in takip etmemesi gereken dosyalar vardır: bağımlılık klasörleri, derleme çıktıları, IDE yapılandırmaları, hassas bilgiler içeren .env dosyaları… .gitignore bu dosyaların listesini tutar.

# Zaten takip edilen bir dosyayı gitignore'a alma git rm --cached .env # Sonra .gitignore'a .env ekle ve commit et # Tüm kullanıcılar için global gitignore git config --global core.excludesfile ~/.gitignore_global # Bir dosyanın neden ignore edildiğini öğren git check-ignore -v dosya.txt
Not gitignore.io adresinde proje türünüze göre (Node, Python, Java, VS Code…) hazır .gitignore şablonları bulunur.

6.6 — Güvenlik ve İyi Pratikler

Git kullanırken en yaygın güvenlik hataları ve nasıl önleneceği:

Şifre ve token commit'lemek — En sık yapılan ve en tehlikeli hatadır. GitHub bile repoları tarıyarak sızan secret'ları tespit eder ve sizi uyarır. Bir kez commit edilip push edilen secret "silseniz" bile tarihçede kalır.

Signed Commits — GPG ile İmzalama: Git, kullanıcı adı ve e-postayı doğrulamaz — herkes istediği ismi yazabilir. GPG imzalama, commit'lerinizin gerçekten sizden geldiğini kriptografik olarak kanıtlar. GitHub'da imzalı commit'ler yeşil "Verified" rozeti alır.

6.7 — Büyük Dosyalar: Git LFS

Git, metin dosyaları için tasarlanmıştır. Büyük binary dosyalar (görsel, ses, video, ML modelleri, Photoshop dosyaları) depoya eklendiğinde repo boyutu şişer ve her clone yavaşlar. Git LFS (Large File Storage) bu dosyaları ayrı bir depoda saklar, ana repoda yalnızca küçük bir pointer bırakır.

# LFS kurulumu (bir kez) git lfs install # Hangi dosya türlerini LFS ile takip et git lfs track "*.psd" git lfs track "*.mp4" git lfs track "*.bin" # .gitattributes güncellendi — commit et git add .gitattributes git commit -m "chore: LFS takibi eklendi" # LFS ile takip edilen dosyaları listele git lfs ls-files
Not GitHub'da LFS depolama ve bant genişliği kotaları vardır. Ücretsiz hesapta 1 GB depolama ve 1 GB/ay bant genişliği verilir. Büyük projelerde ücretli plan gerekebilir.
